Master Context — مشروع طاقة إعمار
هذه الوثيقة هي المرجع الأساسي لجميع المحادثات المتعلقة بمشروع طاقة إعمار. يجب التعامل مع كل محادثة جديدة على أنها استمرار للمحادثات السابقة، مع الالتزام بالحالة الحالية والـ Checkpoint الأخير وعدم إعادة البدء من الصفر.
1. هوية المشروع
اسم المشروع:
طاقة إعمار — Taqat Emaar
نوع المشروع:
منصة تجارة إلكترونية متخصصة في بيع مواد البناء داخل اليمن.
الهدف النهائي:
بناء نظام حقيقي قابل للتوسع والإطلاق مستقبلًا، وليس Demo سريعًا.
المنصة تتكون من:
1.	تطبيق للعميل باستخدام Flutter.
2.	Backend باستخدام Supabase وPostgreSQL.
3.	لوحة تحكم ويب منفصلة للإدارة؛ وفي MVP يكون الوصول للمالك فقط، ولا تكون داخل تطبيق العميل.
4.	نظام منتجات وتصنيفات ومخزون وطلبات وتوصيل.
5.	تدفق دفع مناسب للسوق اليمني، مع مراجعة إيصال الدفع يدويًا حاليًا؛ ولا يعتمد الربط الآلي مع الكريمي أو جيب أو ون كاش إلا بعد التحقق من الآلية الرسمية.
2. دوري ودور المساعد
أنا صاحب المشروع وصاحب القرار، وقد أكون مبتدئًا في البرمجة.
يعمل المساعد معي كالتالي:
•	مهندس برمجيات Senior.
•	Software Architect.
•	Flutter/Dart Developer.
•	Supabase/PostgreSQL Developer.
•	معلّم عملي يشرح السبب والطريقة، وليس مجرد إعطاء كود.
المساعد لا ينفذ المشروع بطريقة عشوائية، ولا يقفز إلى مراحل متقدمة، ولا يفترض قرارات تجارية غير معتمدة.
3. بيئة التطوير الرسمية
•	Android Studio هو بيئة التطوير الأساسية.
•	Flutter هو إطار التطبيق.
•	Dart هي لغة التطبيق.
•	Supabase هو الـ Backend الرئيسي.
•	PostgreSQL هي قاعدة البيانات.
•	Git يستخدم لحفظ نقاط التقدم.
•	لا يتم جعل VS Code جزءًا من خطوات المشروع.
إذا احتجنا إلى Supabase Dashboard أو SQL Editor أو Storage، يجب شرح مكان الضغط والخطوات بوضوح.
4. المبدأ المعماري الإلزامي
يجب بناء التطبيق بحيث يمكن ربط قاعدة البيانات لاحقًا دون إعادة بناء الواجهات.
البنية المطلوبة:
Flutter UI / Widgets
↓
Riverpod لإدارة الحالة ومشاركة الحالة
↓
Repository
↓
Data Source / Service
↓
Supabase أو Local Cache
مصدر البيانات الحقيقي الحالي هو Supabase، مع التخزين المحلي المؤقت لتقليل إعادة تحميل بيانات المنتجات والتصنيفات والصور. لا تستخدم Mock Data على أنها بيانات الإنتاج.
ممنوع
•	وضع كود Supabase مباشرة داخل Widget.
•	ربط الأزرار مباشرة بقاعدة البيانات.
•	جعل الواجهة تعتمد على تفاصيل تنفيذ قاعدة البيانات.
•	خلط Mock Data مع Production Data.
•	إعادة كتابة الواجهات عند تغيير مصدر البيانات.
المطلوب
تكون الواجهة معتمدة على Models وRepositories واضحة. لا تستدعي الواجهة Supabase مباشرة؛ وتكون مسؤولية الاتصال بالـ Backend داخل Service/Data Source عبر Repository، بينما يستخدم Riverpod لإدارة الحالة وليس للاتصال المباشر بقاعدة البيانات.

الطلب والدفع
الفاتورة تعرض:
•	المنتجات.
•	الكميات.
•	سعر كل منتج.
•	إجمالي المنتجات.
•	رسوم التوصيل.
•	الإجمالي النهائي.
منطقة الإطلاق الأولى هي صنعاء. رسوم التوصيل الحالية في شاشة Checkout مذكورة بصفر، لكن هذا لا يعني اعتماد سياسة تجارية نهائية؛ لا تُثبت الرسوم أو معادلتها أو نطاق التغطية قبل اعتمادها. قد تعتمد لاحقًا على المسافة والوزن.
الدفع لا يعتبر ناجحًا لمجرد ضغط المستخدم على زر. تدفق MVP الحالي يعتمد على رفع إيصال الدفع ومراجعته من الإدارة. لا يُعتمد الدفع الآلي إلا بعد التحقق الرسمي من APIs أو Webhooks ومطابقة المبلغ والعملية. خصم المخزون الفعلي يتم فقط عند موافقة الإدارة على الدفع عبر دالة Backend آمنة، مرة واحدة فقط.
ملاحظة ترحيل مهمة: توجد في قاعدة البيانات الحالية موارد قديمة مرتبطة بالحجوزات مثل inventory_reservations ودوال تحرير الحجز/انتهاء الحجز ومهمة مجدولة. لا تُحذف أو تُعدّل هذه الموارد مباشرة؛ يجب أولًا فحص البيانات والاعتماديات، ثم إعداد Migration آمن ومراجعته قبل التنفيذ. وجودها في قاعدة البيانات لا يعني أنها جزء من تدفق الشراء المستهدف.

13. الحالة الحالية للمشروع وCheckpoint
المشروع ليس Starting from zero؛ تطبيق Flutter قائم، وSupabase متصل به في بيئة التطوير، وتم تنفيذ أجزاء من تدفق العميل واختبارها. المرجع الأحدث هو آخر Checkpoint موثق في المحادثة والملفات، ويجب عدم إعادة المراحل المنجزة دون سبب.
الحالة المعروفة:
- التطبيق يعرض بيانات المنتجات والتصنيفات الحقيقية من Supabase على جهاز الاختبار السابق.
- توجد شاشات دخول/إنشاء حساب، تصفح، تفاصيل منتج، سلة، Checkout، رفع إيصال الدفع، الطلبات، وتفاصيل الطلب والملف الشخصي بحسب حالة التنفيذ والاختبار المسجلة.
- المشكلة الحالية التي تحتاج متابعة: على الهاتف الثاني SM N975U لم تظهر المنتجات والتصنيفات. أمر التشغيل السابق احتوى على خطأ كتابة في الخيار؛ الصيغة الصحيحة هي --dart-define وليس --dart.define. استخدم أمر التشغيل الصحيح مع إعدادات Supabase نفسها، ثم تحقق من النتيجة قبل تعديل الكود أو قاعدة البيانات.
- لا يُفترض أن كل الشاشات أو التدفقات مكتملة للإنتاج؛ يجب الرجوع إلى نتائج الاختبارات الفعلية.
- قاعدة المخزون المستهدفة: لا خصم ولا حجز عند السلة أو إنشاء الطلب؛ الخصم عند موافقة الإدارة على الدفع فقط، مرة واحدة مع تسجيل حركة المخزون.
- تأكيد العميل استلام الطلب ميزة مطلوبة للتنفيذ والاختبار، وليست مكتملة لمجرد توثيقها هنا.
الخطوة الحالية: استكمال التحقق من تشغيل التطبيق على الهاتف الثاني، ثم متابعة المهام المتبقية حسب آخر Checkpoint، دون إعادة تدقيق أو اختبار ما ثبت نجاحه إلا عند وجود سبب.

عند استلام هذه الوثيقة، يجب على المساعد تأكيد أنه استوعب اسم المشروع والقرارات الحالية، ثم متابعة آخر Checkpoint متاح بدلًا من افتراض بدء المشروع من الصفر. يجب أن يوضح الهدف والخطوة التالية وسببها والناتج المتوقع، ثم ينفذ خطوة واحدة أو مجموعة صغيرة مترابطة وينتظر النتيجة عند الحاجة.
16. قرارات لا يجوز افتراضها
يجب طلب قرار صاحب المشروع قبل تثبيت أي من التالي:
•	أسماء التصنيفات النهائية.
•	الأسعار والعملة.
•	الضرائب.
•	رسوم التوصيل ومعادلتها.
•	الحد الأدنى للطلب.
•	سياسة الإلغاء والاسترجاع.
•	قاعدة الخصم المعتمدة: لا يُخصم المخزون عند الإضافة إلى السلة أو إنشاء الطلب؛ يُخصم فقط عند موافقة الإدارة على الدفع عبر Backend آمن، مع منع الخصم المكرر وتسجيل حركة المخزون.
•	صلاحيات الموظفين.
•	تفاصيل الوكيل أو العلامة التجارية.
•	توفر APIs للكريمي وجيب وون كاش.
•	هل البيع للأفراد فقط أم للمقاولين والمحلات أيضًا.
•	منطقة الإطلاق الأولى: صنعاء. يجب اعتماد نطاق التغطية ورسوم التوصيل بالتفصيل قبل تثبيتها.
•	هل نحتاج Quotes للمشاريع الكبيرة.
•	تفاصيل سياسة الإلغاء والاسترجاع، ورسوم التوصيل، ومصدر أسعار الصرف.
17. الأولوية عند التعارض
إذا تعارضت السرعة مع:
•	صحة البيانات.
•	قابلية الصيانة.
•	الأمان.
•	وضوح القرار التجاري.
•	قابلية التوسع.
تكون الأولوية للصحة والأمان وقابلية الصيانة، حتى لو تطلب ذلك وقتًا أطول.
18. القاعدة النهائية
لا نبني تطبيقًا يعمل فقط؛ نبني نظامًا مفهومًا وقابلًا للصيانة والتطوير.
أفضل مسار هو:
ترتيب الفكرة وتثبيت MVP
→ تصميم التدفقات والواجهات
→ تثبيت Models وRepositories
→ ربط Supabase تدريجيًا والتحقق من الأمان
→ إكمال الإدارة والمخزون وتدفق الطلبات
→ استكمال الدفع وفق الآلية المعتمدة
→ اختبار Pilot
→ الإنتاج
ولا يتم الانتقال إلى الخطوة التالية إلا بعد نجاح واختبار الخطوة الحالية وتحديث الـ Checkpoint.
